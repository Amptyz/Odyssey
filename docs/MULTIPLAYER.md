# 房间联机与波次恢复

本文对应首版 2–4 人好友 PVE 联机。当前房间协议为 `ember-coop-6`，新增每玩家独立 `phase / scene` 交互快照、保留 `basicAttack` 与动作信号；旧客户端需刷新，中转需同步更新并重启。恢复格式为 v4：普攻形式从余烬列表重建，旧存档中的武器不会授予远程形式。单人仍走原来的 LocalTransport；联机为**房主权威计算 + WebSocket 中转 + 波次恢复点**。目前完成本机服务与浏览器联调，没有部署公网服务。

## 方案依据

房间码是房间目录的索引，不等于玩家的 IP 地址。互联网玩家都主动连接中转服务，不需要在家用路由器上开放端口。直连通过 NAT 穿透在部分网络也能成功，所以并非所有连接都必须中转；第一版统一中转是为了连接路径明确、便于诊断。后续可增加 WebRTC 直连 / TURN 兜底，不改战斗规则。

可借鉴的公开实现：

- [Steam Networking](https://partner.steamgames.com/doc/features/multiplayer/networking)：大厅配合网络消息，可以由一位玩家担任主机；新接口默认使用 Valve 中转网络，也支持适当条件下的直连。这是架构参考，本项目未接入 Steam SDK，不能据此声称网页可以免费使用 Steam 中转。
- [Unity 房间加入与重连](https://docs.unity.com/en-us/mps-sdk/join-session)：区分短房间码、成员身份和重连。房间码用于邀请，原角色恢复需要持有原身份。
- [Unity 主机迁移](https://docs.unity.com/en-us/mps-sdk/session-host-migration)：连接服务与游戏状态迁移是两层工作。仅替换房主 ID 或重新分配中转连接，不能恢复战斗。
- [Factorio 延迟处理](https://factorio.com/blog/post/fff-302)：本地预测可改善手感，但预测与权威状态仍要校正。Factorio 的确定性模拟架构不应直接套进本项目。

本项目第一版采用状态同步，未实现确定性锁步或完整的客户端预测 / 回滚。远端单位位置按两次快照插值，避免直接跳动；普攻和技能的命中、伤害、金币仍由房主计算。中转链路会增加网络往返，WebSocket 基于可靠有序传输，丢包可能阻塞后续消息；强实时射击需求需要继续评估 WebRTC 数据通道及本地预测。

成本主要是在线房间数 × 每房间流量 × 在线时长，加上恢复点存储。服务不运行怪物 AI、碰撞或技能模拟，但并非零成本。代码尚未提供公网流量 / 并发压测结果，不能给出可靠月费或连接成功率。专服也可以一台机器运行多个房间，不应按“一房一台云主机”估算。

## 玩家流程

1. 进入网页，选好地图，打开左上角「联机房间」，填写名字并创建房间。
2. 将 6 位房间码发给队友。队友打开相同版本、连接相同中转服务，输入房间码加入。
3. 房主点击「开始 / 继续试炼」。每个人独立买装备，所有参与玩家确认后开战。
4. 进入营地后每人靠近余烬按 F 选择；全员在出发点范围内，由房主按 F 开始。清场后按地图配置出现余烬或休息点；商人和余烬都需要主动互动。见 [场景指南](SCENES.md)。
5. 原成员短暂掉线时暂停并自动重连。浏览器刷新后，在面板用保留的房间码重新加入；原身份仍会找到原角色。
6. 房主无法回来时，原队友点击「从该房间进度续玩」，得到**新房间码**并成为房主。队友用新码加入，点击继续后从保存点恢复。旧房间与新房间是不同的分支，不互相覆盖。

新玩家只能在开局准备阶段加入；开始后只允许原成员重连。首版没有账号系统：浏览器本地保存随机身份密钥，服务器保存其 SHA-256 摘要；显示名字与房间码都不能替代身份。清空浏览器数据、换浏览器或换电脑不会自动继承旧角色。不要将身份密钥写入日志、URL 或共享存档。

ESC 打开自己的操作设置，不能暂停全队。房间断线 / 房主切到后台时则冻结战斗；房主可以在面板跳过离线队友继续。被跳过的角色不参与碰撞和敌人选敌，原成员回来后恢复角色。联机禁止通过输入协议调用开发者面板、修改地图或直接重开世界。

## 保存与恢复语义

用户选择的首版规则是：**允许重新开房，从最近波次继续**，不承诺恢复到掉线的精确帧。

| 保存时机 | 恢复行为 |
| --- | --- |
| 营地 / 休息点、商店交易 | 保留角色、库存、装备、金币、个人面板与最近交互位置 |
| 清怪并集合出口后进入奖励 | 保留已经完成的波次、发放的金币和每人固定的候选，不重复发钱 |
| 选择余烬 / 待替换技能 / 确认槽位 | 保留每人的选择，已领取者可继续移动，出发时在集合圈等队友 |
| 新波次开始 | 保存全队构筑、生命、起点及生成随机状态，战斗中不覆盖这个恢复点 |
| 最终奖励确认 | 保留通关状态 |

恢复战斗时按mapId/wave重建固定关卡敌群与全队出生方阵、重新计时技能，清除旧输入；**本波已造成伤害、走过的位置与战斗中消耗会回到波次起点**。跨波保留的金币、装备、主动技能、余烬和已完成波次不会因普通重连而清空。掉线发生在保存确认前，恢复的仍是上一个已确认点，不能将尚未送达的操作承诺为已保存。

中转服务按序保存：写临时文件 → fsync 文件 → 原子 rename → fsync 目录 → 回送 `saved`。房主在恢复点未确认期间停止推进战斗；队友收到确认后才更新本地备份。服务进程重启可从磁盘恢复房间与身份映射；服务器磁盘损坏 / 数据目录丢失仍需运维备份。客户端缓存和下载的 JSON 是进度副本，目前没有通用导入 UI，也不包含原成员身份凭证。

## 源码职责

路径相对于 `EmberDemo/assets/scripts/ember/`，服务脚本另列。

| 文件 | 职责 |
| --- | --- |
| `platform/room-protocol.ts` | 协议版本、成员、房间、消息和远程命令白名单 |
| `platform/RoomTransport.ts` | 单人 / 房间适配、房主固定模拟调度、重连、输入序号、存档确认、远端快照插值 |
| `platform/RoomPanel.ts` | 浏览器房间码 UI；不实现游戏模拟，不是第二个 Web 游戏 |
| `simulation/GameWorld.ts` | `players` 内独立 PlayerState、同一 actors / CollisionWorld、共同关卡、出口集合与等待规则 |
| `simulation/RunCheckpoint.ts` | 版本化恢复格式、拷贝与导入校验；与展示快照分开 |
| `combat-core/CombatEngine.ts` | `perksFor(playerId)` 区分余烬；暴击、附伤、规则触发按事件来源玩家读取 |
| 根 `scripts/relay-server.ts` | WebSocket 接入、6 位码、成员身份、输入路由、快照转发、心跳、磁盘保存；不运行战斗 |

为兼容已有单人测试，`world.hero / equipment / loadout / cooldowns` 仍指向初始玩家 `hero`；新增多人逻辑必须使用 `players.get(playerId)`、`command(command, playerId)`、`snapshot(playerId)`，不能把这些单人便利字段当成当前操作者。

CombatEngine 仍是一个共享事件引擎，状态计时每个 tick 只推进一次。伤害属性按 sourceId / targetId 查对应玩家；规则计数、去重包括来源玩家，不把一个玩家的装备或海克斯用于全队。敌人选择最近的存活参与玩家，命中仍走同一个 CollisionWorld。第一版没有人数动态难度、队友复活交互或战利品分配系统。

当前协议为 `ember-coop-6`，`RunCheckpoint.version` 为 `4`。每名玩家保存六个通用装备栏和purchaseOrder，按购买顺序重建外观，按各自余烬重建普攻形式。每名玩家各自持有 AttributeSet；恢复点保存当前法力和额外永久属性来源，装备 / 余烬按 ID 重建后再加入永久来源。导入禁止伪装为 equipment:/perk:/temporary:/developer 的来源；不保存解析后的最终 AD/AP，避免恢复时重复加成。旧 v1/v2/v3 恢复点明确拒绝，没有静默迁移。

`WorldSnapshot` 仍然不是任意时刻的可恢复存档。`RunCheckpoint` 只在稳定阶段 / 波次起点生成，包含生成敌人前后的随机状态、实体编号，以及各玩家构筑与阶段确认；不要把战斗中途快照伪装成波次存档。新增影响跨波进度的字段必须同步保存、校验、恢复和测试。修改不兼容协议或内容时提升 `ROOM_VERSION` / 存档版本，禁止静默接受旧客户端。

网络边界只接受白名单命令，身份由连接确定，客户端不能用消息中的 playerId 控制别人。输入序号过滤重复请求；断线、恢复和阶段切换清理持续移动 / 连击，超时未收到输入也会停止远端角色。帧与保存消息仅接受当前房主。房主仍受玩家控制，不具备专服的结算可信度。

## 本机运行与部署边界

先按 README 构建 Cocos Web Desktop，然后开两个终端：

```bash
pnpm play
pnpm relay
```

网页默认 `http://127.0.0.1:8080/`，中转默认 `ws://127.0.0.1:8787`。浏览器面板「连接设置」可指定中转。两个测试玩家请用不同浏览器配置 / 隐私窗口；相同本地身份在两个窗口同时连接会替换旧连接。

服务变量：

| 变量 | 默认 | 用途 |
| --- | --- | --- |
| `RELAY_HOST` | `127.0.0.1` | 监听地址；对外部署优先由反向代理接入 |
| `RELAY_PORT` | `8787` | 服务端口 |
| `RELAY_DATA_DIR` | `.ember-relay` | 必须使用持久磁盘 / 容器持久卷，包含身份摘要与存档 |
| `RELAY_ORIGINS` | 未设置 | 可接受网页 Origin 列表，逗号分隔；公网设置成自己的游戏域名 |

`GET /health` 返回服务版本。公网需要可访问的 HTTPS 游戏页面和 WSS 中转地址 / 反向代理，所有玩家使用同一服务。**部署中转的机器需要公网入口，房主与队友不需要。** 不把别人的 `127.0.0.1` 当作可共享地址；当前 `pnpm play` 也只监听本机。没有在本次开发中租用主机、配置域名或部署公网环境。

浏览器房主切后台会发送不可用状态并暂停；模拟调度虽已独立于 Cocos 渲染帧，浏览器 / 操作系统仍可能挂起计时器。不能保证锁屏、睡眠后继续运行。客户端在快照长时间未到达时停止展示战斗推进，服务器心跳超时会标记成员离线。


后续优先测量公网 RTT / 丢包 / 实际房间带宽，完成本地移动预测、输入确认后的校正和必要的差量 / 压缩，再评估 WebRTC 直连、中转区域选择与并发容量。自动无缝更换房主不是这一版的恢复规则；未来需要完整战斗状态与接管协议，不能只在面板上换名字。

18 件装备 ID 由同一货架目录校验；当前房间协议为 ember-coop-6，恢复点为 v4，旧版客户端与存档不能直接使用。每位玩家的 equipmentPassives 通过 PlayerView 独立覆盖，客机不会显示房主的符击 / 石息。被动实时 CD / 蓄能 / 攻击锁不写入稳定阶段恢复点；恢复新关时重建为就绪、无蓄能，符合当前关卡起点恢复语义。
